[] 1. 产品概述
[] 1.1 产品背景
[] 个人在长期工作过程中会产生大量分散的信息，包括：
[] 周报、月报、工作总结。
[] 项目资料、需求文档、产品方案。
[] 系统和功能模块的建设记录。
[] 日常工作事项、问题处理和沟通记录。
[] 项目成果、个人贡献和经验总结。
[] 这些资料通常分散在不同文件、文档和系统中，缺乏统一的整理和关联。
[] 随着工作时间增长，个人虽然积累了大量经验，但很难快速回答以下问题：
[] 自己长期参与和负责过哪些项目、系统和功能？
[] 自己实际具备哪些专业能力？有哪些工作案例可以证明？
[] 自己的能力和职责范围在不同阶段发生了什么变化？
[] 自己有哪些明显的优势、工作特点和待提升方向？
[] 过去完成的工作中，哪些可以作为简历、述职和晋升材料？
[] 如何将长期积累的工作经验转化为清晰、可展示的个人职业价值？
[] 传统笔记工具主要解决资料存储和知识整理问题，传统简历工具主要解决职业经历展示问题，二者都无法完整满足长期个人成长档案的需求。
[] 因此，需要建立一套以个人真实工作经历为基础，通过 AI 辅助整理和分析，持续构建个人能力画像与成长轨迹的系统
[] 1.2  产品定位
[] 本产品是一套以真实工作经历为基础、以 AI 为整理和分析助手的个人成长档案系统。
[] 系统将分散的工作资料转化为结构化的个人档案，建立项目、系统、功能模块、工作事项、成果案例、能力证据和个人特征之间的关联。
[] 通过持续积累和分析，形成可追溯的个人职业能力画像、个人特征画像和成长历程，并支持简历、述职、晋升等个人材料的生成。
[] 1.3 核心价值
[] 统一沉淀： 将分散的工作资料整理成统一的个人档案。
[] 持续关联： 将跨时间、跨文档的相关工作事项串联起来。
[] 能力识别： 从真实工作案例中提炼个人能力及其表现。
[] 成长可视化： 展示能力、职责、工作领域和项目经验的变化。
[] 证据可追溯： 所有重要结论都能查看对应的原始资料。
[] 成果可复用： 将历史工作成果转化为简历、述职和晋升素材。
[] 1.4 产品设计原则
[] 原始资料与整理结果分离，原始内容不得被 AI 覆盖。
[] 结构化档案独立于 Agent，避免数据绑定某一个模型或工具。
[] 重要数据必须保留来源和关联关系。
[] AI 负责提出整理和分析建议，用户负责确认正式档案变更。
[] 事实、推断和评价必须区分。
[] 能力判断必须有工作证据支持，不能仅凭 AI 主观评分。
[] 允许用户随时修正项目归属、个人贡献、能力判断和画像内容。
[] 所有正式数据应支持导出和迁移。
[] 2. 产品目标与范围
[] 2.1 主要目标
[] 第一版需要形成完整的个人成长档案闭环：
[] 原始资料导入 → AI 内容提取 → 工作事项整理 → 项目及模块关联 → 成果提炼 → 能力证据关联 → 个人画像生成 → 成长趋势分析 → 个人材料输出。

[] 跨资料工作主题归并。
[] 工作经历档案。
[] 成果案例管理。

[] 复杂的职业市场分析和岗位实时匹配。
[] 3. 用户使用场景
[] 日常资料导入
[] 用户每周上传周报或直接输入工作记录。
[] 系统自动识别其中的工作事项、项目、系统、模块、工作成果和时间信息，形成待审核建议。
[] 用户确认后，正式档案更新。
[] 跨时间工作归并
[] 用户不同月份的周报可能反复提到同一个项目或系统。
[] 系统应识别相关事项，并将其关联到已有项目或持续工作主题，而不是每次都创建新的项目。
[] 用户可以查看该主题下的完整工作时间线、原始资料和阶段性成果。
[] 个人能力分析
[] 系统根据已确认的工作事项和成果案例，识别相关能力表现。
[] 用户可以查看某项能力的定义、相关案例、能力证据、时间变化和判断依据。
[] 个人特征分析
[] 系统根据长期工作记录，分析工作风格、思维方式、行为习惯和兴趣倾向。
[] AI 先提出画像假设，用户可以确认、修改或否定。
[] 成长分析
[] 用户查看某段时间内的能力变化、职责变化、工作领域分布、项目经验和代表性成果。
[] 个人材料生成
[] 用户选择简历、述职、晋升或项目介绍等用途，指定时间范围和重点方向。
[] 系统从已确认档案中提取素材，生成可编辑的材料，并保留引用来源。

[] 6. 产品功能架构
[] 6.1 功能架构说明
[] 个人成长档案系统围绕个人工作经历、职业能力、个人特征和成长轨迹展开，通过 AI Agent 对长期工作资料进行解析、提取、归纳和关联，将分散的工作记录逐步沉淀为结构化的个人成长档案。
[] 产品功能主要分为八个模块：
[] 成长总览：集中展示个人档案和成长情况。
[] 工作经历档案：管理项目、系统、功能模块及具体工作事项。
[] 职业能力画像：记录职业能力及其对应的实际表现证据。
[] 个人特征画像：沉淀个人工作风格、习惯、优势和待发展方向。
[] 成长分析：分析能力变化、工作经历变化及阶段性成长情况。
[] 成果案例中心：整理具有代表性的项目成果和工作案例。
[] 个人材料中心：基于已有档案生成简历、述职、晋升等材料。
[] 资料与 AI 管理：管理原始资料，并通过 AI 完成信息提取、关联、审核和档案更新。
[] 各模块共享同一套底层数据，避免重复记录，并支持从分析结论回溯至具体工作事项和原始资料。
[] 6.2 成长总览
[] 模块定位： 作为系统首页，集中呈现个人工作经历、能力画像、代表性成果和成长趋势，帮助用户快速了解自己的整体发展情况。
[] 主要功能：
[] 个人成长摘要：展示当前职业经历、主要工作领域和整体成长情况。
[] 近期工作动态：展示近期新增或更新的工作事项、项目和成果。
[] 核心能力概览：展示当前主要能力及其对应的证据积累情况。
[] 代表项目与成果：展示具有代表性的项目经历和工作成果。
[] 成长阶段与趋势：展示不同时间阶段的工作职责、能力变化和成长轨迹。
[] 6.3 工作经历档案
[] 模块定位： 作为个人工作经历的结构化记录中心，完整记录参与过的项目、负责的系统与功能模块，以及具体工作内容和职责变化。
[] 主要功能：
[] 项目管理：记录项目背景、目标、参与时间、项目状态、个人职责和项目成果。
[] 系统与功能模块管理：记录工作涉及的业务系统、产品及其下属功能模块。
[] 工作事项记录：记录具体工作内容、问题背景、处理过程、个人角色和最终结果。
[] 持续工作主题归并：将不同周报、月报中反复出现的相关工作归纳为持续性主题，同时保留原始事项。
[] 职责与贡献记录：区分个人负责、主导、参与、协助等不同角色，记录实际贡献范围。
[] 6.4 职业能力画像
[] 模块定位： 基于真实工作经历和成果证据，逐步建立个人职业能力档案，展示能力构成及其实际表现。
[] 主要功能：
[] 能力分类与词典：建立统一的能力分类、名称、定义和评价参考。
[] 能力证据管理：将工作事项、项目经历和成果案例关联至具体能力。
[] 能力表现分析：分析用户在实际工作中表现出的能力和行为。
[] 能力维度评价：结合工作复杂度、独立程度、责任范围、成果质量等维度分析能力表现。
[] 能力变化趋势：展示不同时间阶段的能力证据积累及变化情况。
[] 能力评价不能仅根据工作事项数量判断，应以实际工作表现和可追溯证据为依据。
[] 6.5 个人特征画像
[] 模块定位： 从长期工作记录和用户主动输入中，逐步整理个人工作习惯、思维方式、行为特点及个人优势。
[] 主要功能：
[] 个人特征记录：记录相对稳定的个人工作特点。
[] 工作习惯与风格：分析任务处理、沟通协作、问题解决和决策等方面的表现。
[] 优势与待发展方向：整理已体现出的优势，以及仍有提升空间的方面。
[] 特征证据与反例：记录支持某项特征判断的具体案例，同时保留不符合该判断的反例。
[] 自我评价与 AI 分析：区分用户主动描述和 AI 根据资料得出的分析结论。
[] AI 对个人特征的判断属于分析建议，未经用户确认不直接作为正式档案结论。
[] 6.6 成长分析
[] 模块定位： 基于长期积累的工作经历、能力证据和成果案例，分析个人在不同时间阶段的变化，形成可视化的成长记录。
[] 主要功能：
[] 能力成长曲线：展示各项职业能力在不同阶段的证据积累和表现变化。
[] 经历成长曲线：展示工作领域、项目类型、职责范围及工作复杂度的变化。
[] 工作领域分布：分析不同业务领域、系统和项目中的工作投入与经历分布。
[] 成长阶段分析：根据职责、工作内容、能力表现等变化划分不同成长阶段。
[] 阶段性总结：生成指定时间范围内的工作经历、代表成果和能力变化总结。
[] 成长分析需要区分资料数量增加与实际能力提升，不能将新增记录直接等同于能力成长。
[] 6.7 成果案例中心
[] 模块定位： 将分散在周报、月报和项目记录中的重要成果整理为独立案例，形成可复用、可追溯的个人成果库。
[] 主要功能：
[] 成果案例提取：从工作事项和项目经历中识别具有沉淀价值的成果。
[] 背景与问题：记录成果产生的业务背景、原始问题和挑战。
[] 行动与解决方案：记录个人采取的行动、解决思路和实施过程。
[] 结果与量化指标：记录实际产出、业务影响和可验证的数据。
[] 个人贡献与经验沉淀：区分个人贡献和团队成果，整理可复用的方法与经验。
[] 6.8 个人材料中心
[] 模块定位： 基于已经确认的个人档案和成果案例，按不同使用场景生成个人职业发展材料。
[] 主要功能：
[] 简历生成：根据目标岗位和指定时间范围，提取相关工作经历、能力和成果。
[] 项目经历介绍：将项目档案整理为适合简历或面试使用的项目描述。
[] 述职与晋升材料：根据指定周期整理工作成果、个人贡献、能力表现和成长情况。
[] 年度工作总结：汇总指定年度的重点工作、项目成果和能力变化。
[] 材料版本与引用来源：保留生成材料的版本，并支持查看内容对应的档案和原始证据。
[] 所有生成材料应以已有档案为依据，不得擅自补充未经证实的职责、成果或量化指标。
[] 6.9 资料与 AI 管理
[] 模块定位： 作为系统的信息输入和 AI 处理中心，负责接收原始资料、提取结构化信息，并通过人工审核保证正式档案的准确性。
[] 主要功能：
[] 原始资料导入：支持周报、月报、文档和手动记录等资料的导入。
[] 资料分类管理：管理原始资料的类型、时间、来源及处理状态。
[] AI 内容提取：识别资料中的工作事项、项目、职责、问题、行动和成果。
[] 智能关联与归并：匹配已有项目、系统、功能模块和持续工作主题，提出新增、关联、合并或拆分建议。
[] AI 变更审核：展示 AI 提取和分析后提出的档案变更，支持确认、修改、拒绝和补充说明。
[] 数据备份与迁移：支持档案数据导出、备份和迁移，避免长期数据依赖单一 AI 工具。
[] AI 只能提出档案变更建议，正式档案的新增、修改、合并和删除均应经过用户确认。
[] 7. 产品实施建议
[] 建议按以下顺序实施，但不将其视为不同功能版本：
[] 确定核心数据模型。
[] 确定原始资料存储和来源追溯方式。
[] 建立项目、系统、模块、工作事项等档案。
[] 建立 AI 提取、匹配、归并和审核机制。
[] 建立能力词典和能力证据模型。
[] 建立个人特征画像。
[] 建立成长曲线和成长阶段分析。
[] 建立成果案例和个人材料生成。
[] 建立 API / MCP / CLI 接入。
[] 完成数据备份、迁移和安全验证。
[] 最终交付物应包括：
[] 可用的个人成长档案系统。
[] 完整的数据模型和字段说明。
[] Agent 工作流及提示词配置。
[] 数据导入和审核流程。
[] 个人画像与成长分析界面。
[] 个人材料生成能力。
[] 数据备份、导出和迁移机制。
[] 产品最终目标： 让个人长期积累的工作资料不再是分散的历史记录，而成为一份持续更新、真实可信、可追溯、可分析、可迁移的个人职业成长资产。
[] 8. Agent Design Guidelines｜界面与前端开发约束
[] 8.1 信息组织与界面设计
[] 先理解页面的目的、用户任务和信息层级，再决定布局。
[] 突出核心信息和主要操作，避免无意义的小字、重复提示和装饰性字段。
[] 视觉设计应当美观、清晰、有品质，不局限于极简或传统后台风格。
[] 合理使用卡片、留白、分隔线、背景、图标、图表等元素，避免为了分组而滥用卡片。
[] 数据分析和成长可视化应重视视觉表现，保证图表美观、易读且能准确表达数据。
[] 8.2 文案规范
[] 使用清晰、自然、准确的产品语言，避免过度口语化、模糊表达和难以理解的专业术语。
[] 文案应让用户明确知道：当前是什么状态、可以做什么、操作后会发生什么。
[] 按钮、菜单、标题、字段名称、提示语等应简洁且含义明确。
[] 同一功能、状态或操作在不同页面中应保持命名一致，避免同一概念出现多种叫法。
[] 不要为了填充界面而生成没有实际意义的说明文字。
[] 不确定文案表达是否准确时，优先结合具体业务场景重新组织，不要机械套用模板。
[] 8.3 颜色与视觉规范
[] 建立统一的颜色体系，区分品牌色、基础色、状态色和数据分类色。
[] 可以参考成熟设计系统、专业数据可视化方案和优秀产品案例，不局限于固定配色。
[] 不要机械地给每个模块分配一种颜色。
[] 图表配色应考虑数据类型、系列数量、颜色协调性和可访问性。
[] 页面之间应保持统一的视觉语言。
[] 8.4 数据真实性与可视化
[] 根据数据类型和分析目的选择合适的图表，不要为了视觉效果强行添加图表。
[] 图表应具备清晰的标题、图例、单位和时间范围。
[] 不得虚构指标、评分、趋势、统计结果或数据。
[] 字段必须有明确的数据来源、计算规则或实际用途。
[] 区分客观事实、AI 推断和评价结论，重要分析应支持来源追溯。
[] 8.5 前端组件化与复用
[] 页面开发前先检查现有组件、页面模板和布局，不要重复造轮子。
[] 当相同或相似的组件在三个及以上位置使用时，应评估是否抽取为公共组件；不以使用次数作为唯一标准，还要考虑复用价值、维护成本和差异程度。
[] 对于结构相同、仅数据字段或内容插槽不同的页面，应优先考虑使用统一组件，通过配置、属性或插槽处理差异。
[] 重点评估以下公共能力：
[] 页面 Layout：统一页面整体布局、内容区域、页面标题、操作区和导航结构。
[] 列表组件：统一列表结构、分页、筛选、排序、空状态等，通过字段配置或插槽适配不同业务。
[] 表单组件：统一表单布局、字段渲染、校验、提交和交互反馈。
[] 路由与菜单：统一路由组织、菜单配置、选中状态和权限控制，避免页面各自维护一套。
[] 通用交互组件：统一弹窗、抽屉、确认操作、搜索、筛选等常见交互。
[] 组件应具备合理的扩展能力，避免为了复用而设计过度复杂的万能组件。
[] 公共组件的视觉、交互和行为应保持一致，修改时应考虑对所有使用页面的影响。
[] 8.6 设计参考与规范复用
[] 可以参考 Ant Design、shadcn/ui、IBM Carbon 等成熟设计系统，以及专业的数据可视化方案。
[] 优先复用项目已有的设计 Token、公共组件和页面规范。
[] 不要在不同页面随意发明新的颜色、间距、组件样式或交互方式。
[] 参考外部方案时，应结合当前产品实际情况，不要机械照搬。
[] 8.7 主动调研与外部参考
[] 遇到设计、交互、文案或前端架构问题时，主动搜索互联网，参考成熟产品、开源设计系统、官方技术文档和优秀实践，不要只依赖模型已有知识。
[] 优先参考官方文档、知名开源项目和有实际落地经验的技术方案，避免直接采用来源不明的博客或未经验证的代码片段。
[] 设计方面：调研优秀产品的页面布局、信息层级、配色方案、数据可视化和交互设计。
[] 文案方面：参考成熟产品的内容设计规范、UX Writing 指南和具体业务场景中的表达方式。
[] 前端方面：参考主流框架的官方文档、组件库、设计系统及工程实践，重点关注 Layout、列表、表单、路由、菜单和公共组件的设计。
[] 采用外部方案前，先判断是否适合当前项目的技术栈、业务需求和现有架构，不要直接照搬。
[] 对重要的技术选型或架构调整，说明参考来源、采用理由和可能的影响。
[] 如果现有实现已经合理，不要为了追求新方案而随意重构。
[] 8.8 Agent 开发要求
[] 生成或修改页面前：
[] 理解页面目标、业务场景和用户操作。
[] 检查现有页面、组件、布局和设计规范。
[] 规划信息层级、文案和交互方式。
[] 判断哪些部分可以复用，哪些部分确实需要定制。
[] 确认展示的数据和字段有真实来源。
[] 完成后检查：
[] 信息层级是否清晰，视觉效果是否协调。
[] 文案是否准确、自然、易懂，命名是否统一。
[] 是否存在无意义的小字、字段或重复提示。
[] 是否出现可以复用却重复开发的组件。
[] 公共组件的改动是否影响其他页面。
[] 颜色、布局、交互是否符合项目现有规范。
[] 是否存在虚构数据、指标或没有实际用途的内容。
