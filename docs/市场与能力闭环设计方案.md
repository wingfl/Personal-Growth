# 市场情报与能力闭环设计方案（v0.1 讨论稿）

> 目标：把「外部就业市场数据」接进现有个人成长系统，形成「经历沉淀 → 能力证据 → 市场定位 → 成长建议」的闭环。
> 定位：不是求职/岗位推荐工具，而是让人知道自己**在就业市场里的真实位置**，以及**下一步补什么**。
> 本文只做设计，不改代码；确认后按 P0→P3 分阶段实施。

## 1. 现状与差距

| 层 | 现状 | 差距 |
|---|---|---|
| 资料入库 | 37 篇周报/月报、2559 片段、10 种文档类型 | 缺「会议纪要」类型；PRD/方案可入库但提取规则未针对 |
| 事项与项目 | 541 事项、48 项目、4 系统、6 模块；含问题/过程/结果/我的角色 | 第三方平台（Adjust/DMM/Google/AIHelp）未系统识别 |
| 能力证据 | 10 项能力、703 条证据（394 原文 + 309 链路推断） | 词典是**产品经理专用**；缺复合能力分析 |
| 目标 | `growth_goal` 3 条在跟踪 | 进度手动；与市场差距未打通 |
| 市场数据 | 无 | 岗位样本、薪资基准、要求结构化、趋势全部缺 |
| 配置 | `user_profile` 有 `location_city`/`target_position`（DDL） | 缺现薪/期望薪/年限；方向不能多选；模型文件与实际 DDL 有漂移 |

## 2. 两个关键设计决策

### 2.1 多用户：一库一人（先做），不做多租户

系统现在所有表都没有 `owner_id`，是单用户结构。要支持「不只我自己用」，有两条路：

- **方案 A（推荐）一库一人**：每个人一个 SQLite 文件（`data/profiles/<名字>.db`），Web 启动时选库（`python -m app.web --db ...`），支持导出/导入整库。
  - 优点：零 schema 改动、数据天然隔离、备份/迁移简单、符合本地单机定位。
  - 代价：跨人对比做不了（也不需要）。
- **方案 B 多租户**：所有表加 `owner_id`，做账号与权限。重构面大，当前阶段不值得。

**结论：先 A，并在表设计上不引入跨用户外键，将来要迁 B 时按「一库 = 一个 owner」整体导入即可。**
界面加一个轻量的「档案库」入口：当前库路径、切换、导出备份。

### 2.2 多职业：能力词典按「岗位族」分层

现有 10 项能力（PU/DQ/CO/CG）是产品经理框架，直接给设计/研发用会失真。`capability` 表已有 `framework_name` 字段，正好用来分层：

- 通用层：跨职业都成立的（沟通表达、复盘迁移、项目推进、数据分析……）。
- 岗位族层：产品经理、产品设计、研发、测试、运营各自的要求项（如「第三方平台集成」「系统协同」「技术理解」属于产品/研发的交叉项）。
- `target_role.role_family` 决定默认加载哪套框架；画像页可切换「按当前岗位 / 按目标岗位」两种视角。

迁移：现有 10 项标 `framework_name=产品经理能力框架 v1`，不动数据；新增能力按框架追加。

## 3. 页面收敛：7 页 → 5 页

| 现在 | 收敛后 | 说明 |
|---|---|---|
| 首页 | **首页** | 只留「我现在什么状态 + 最近变化 + 要处理什么」，趋势图并入 |
| 成长档案 | **成长档案** | 事项/项目/资料三 Tab 不变；顶部加「工作构成/活跃热力」两张小图 |
| 数据分析 | （拆掉） | 趋势→首页；构成/热力→档案；阶段对比→能力画像 |
| 能力画像 | **能力画像** | 加「复合优势」区块与「按目标岗位」视角 |
| 成长目标 | **目标与复盘** | 目标 + 待审建议 + 阶段回顾合一，减少一页 |
| 复盘 | （并入目标与复盘） | 建议审阅是复盘的一部分 |
| 设置 | 右上角菜单 | 不再占主导航；含身份/档案库/数据源/常用命令 |
| — | **市场定位（新）** | 岗位样本、薪资带、要求频次、我的差距 |

主导航最终 5 项：**首页 / 成长档案 / 能力画像 / 市场定位 / 目标与复盘**。

市场定位页结构（单页）：
1. 顶部：目标方向 chips（多选）+ 城市 + 现薪/期望薪 + 样本量与更新时间。
2. 薪资带：按 10k 以下 / 10–15k / 15–20k / 20–30k / 30k+ 分档，展示每档岗位数与该档高频要求。
3. 要求频次：Top 15 要求（must/nice 区分），点击展开样本 JD。
4. 我的位置：现薪对应的要求覆盖率、缺口 Top 5、与目标薪资带的差距。
5. 趋势：近 12 周岗位量/中位薪资变化（周更快照）。
6. 边界：样本不足 20 条时只显示「样本不足」，不给结论。

## 4. 数据模型（新增 5 表 + 扩展 1 表 + 复用 2 处）

### 4.1 扩展 `user_profile`
`current_salary`（int，月薪元）、`expected_salary`（int）、`years_of_experience`（real）、`salary_updated_at`。
`location_city` 已有（模型文件需补声明，修 DDL 漂移）。

### 4.2 `target_role`（方向多选，支持自由新增）
`id, name, role_family, city, priority, is_active, keywords(json), origin, created_at...`
预置三条：AI 产品经理 / 产品设计 / 产品经理（`role_family` 分别 product/design/product）；用户可新增任意名称，`role_family` 决定用哪套能力框架。

### 4.3 `job_posting`（岗位样本，不是全量库）
`id, platform, external_id, title, company, city, salary_min, salary_max, salary_months, exp_min, exp_max, education, description, requirements, url, posted_at, retrieved_at, raw_hash, dedupe_key, status`
唯一键：`(platform, external_id)`；无 external_id 时用 `(title, company, city, raw_hash)`。

### 4.4 `job_requirement`（JD 拆出的要求）
`id, job_id, text, capability_id, level(1-5), importance(must/nice), quote, confidence, origin`
由采集后的解析作业生成，先写 `change_proposal`，确认后落库（沿用现有审核链路）。

### 4.5 `salary_benchmark`（报告口径基准）
`id, role_family, level, city, p25, p50, p75, source_report, source_url, year, sample_size`
来源：统计局 + 智联/BOSS/猎聘/脉脉年度报告，人工摘录，界面标注出处与年份。

### 4.6 `market_snapshot`（周更趋势）
`id, week, role_id, city, job_count, salary_median, salary_p25, salary_p75, top_requirements(json), created_at`
每周采集后写一条，用于趋势与「需求变了没有」。

### 4.7 复用
- 第三方平台：`tag`/`tag_link` 打「平台」标签（一条事项可挂多个），或 `business_system(system_type=platform/tool)`。
- 能力：`capability_evidence` 不动，市场要求通过 `job_requirement.capability_id` 对齐同一套能力。

## 5. 采集器设计（周更）

### 5.1 位置与边界
- 采集器放 `collector/`，**不放进 `app/`**：`app/` 必须保持零第三方依赖（质量闸门第 5 步），采集器可以用 requests/解析库，坏了也不影响产品运行。
- 采集器只产出标准格式 `jobs-YYYYWW.jsonl`，由 `python -m app.cli market ingest <file>` 入库；采集与产品解耦、可替换。

### 5.2 流程
1. 按 `target_role.keywords + city` 生成查询（如「AI产品经理 杭州」）。
2. 列表页 → 详情页，限速（≥2s/请求），遇验证码/登录墙即停并记录。
3. 原始 JSON/HTML 存 `data/market/raw/<week>/`，规范化后写 jsonl。
4. 入库去重（platform+external_id / hash），写 `retrieved_at`，重复只更新薪资与状态。
5. 每周一 08:00 由计划任务触发（Windows 计划任务或 DSH schedule），失败可重入。

### 5.3 采集范围（建议）
- 优先：猎聘（有官方 MCP，可先走官方通道）、BOSS（列表+详情字段最全）。
- 次选：智联、51job。
- 明确不碰：简历、聊天、投递记录、登录态个人信息。

### 5.4 合规护栏（必须写进代码）
- 只采公开职位信息；限速；不绕过验证码；不伪造登录态。
- 数据仅本地个人使用，不入公共库、不再分发；提供「一键清空市场数据」。
- 平台 ToS 与 robots 的风险已知：这是**个人自用**的取舍；若将来对外提供，必须换成授权数据源。

### 5.5 期望数据量
每次采集 200–500 条岗位，12 周约 3–5k 条样本，足够做频次与薪资带分析；单条 JD 解析成本可控（批量 20–30 条/次）。

## 6. 匹配与建议逻辑

1. **要求 → 能力**：规则表优先（关键词→能力 code），未命中的走 LLM，产出 `job_requirement`。
2. **我的覆盖**：按能力统计已确认证据数、最高强度、最近时间；推断证据单独标注，不计入「有实证」。
3. **差距分级**：must 未覆盖（红）> 只有推断证据（黄）> 覆盖但强度低（灰）> 已覆盖（绿）。
4. **薪资带对比**：现薪档 vs 目标档的要求差集，输出「涨到 20k 需要补的 3 件事」。
5. **成长建议**：差距 → 生成 `growth_goal` 建议（不自动写入，需确认）；与现有目标页打通。
6. **不打总分**：只给覆盖率、缺口清单、证据强度，延续「不生成无依据分数」的原则。

## 7. 还缺什么（除上面已列）

- `document_type` 增 `meeting_notes`（会议纪要）；提取提示词补「只取决策/结论/待办」。
- 第三方平台识别规则（Adjust、DMM、Google、AIHelp、Steam、Meta 等常见平台词表）。
- 复合能力分析：跨项目共现的能力组合（≥3 个项目、≥5 条证据）→「差异化优势」。
- 档案库管理：切换/导出/导入（多用户方案 A 的配套）。
- 市场页的空态与样本不足规则。
- 定时任务与失败告警（采集失败不阻塞主系统）。

## 8. 实施优先级

| 阶段 | 内容 | 预估 | 验收 |
|---|---|---|---|
| P0 | profile 扩字段（城市/现薪/期望/年限）+ `target_role`（多选+自由新增）+ `market ingest`（贴 JSONL/手动粘贴）+ 迁移 | 2–3 天 | 配置能存、JD 能入库、界面能显示 |
| P1 | JD 解析 → `job_requirement`（先建议后确认）+ 市场定位页（薪资带/频次/差距）+ 5 页导航收敛 | 4–6 天 | 12k 档要求覆盖率与缺口可见 |
| P2 | 采集器 v1（猎聘/BOSS）+ 周更 + `market_snapshot` 趋势 | 3–5 天 | 连续两周有快照 |
| P3 | 复合优势 + 差距→growth_goal 建议 + 多档案库切换/导出 | 3–4 天 | 目标页出现市场驱动的建议 |

依赖：P1 依赖 P0；P2 可与 P1 并行；P3 依赖 P1/P2。
