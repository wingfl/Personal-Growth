# 技术选型与架构决策记录（ADR）

本文件记录本项目的技术选型与架构决策。每条决策包含**背景 / 决策 / 理由 / 后果 / 曾考虑的替代方案**。
记录的是「当前为什么是这样」，不是「未来应该怎样」。状态只有三种：**已采纳**、**已取代**、**待定**。

读者：后续维护者（包括未来的我）。当你要改动这里记录的决策时，先读对应条目，再在文件末尾追加一条新 ADR
说明「为什么改」，而不是直接删掉旧结论。

---

## 技术选型总览

| 领域 | 选择 | 主要理由 | 曾考虑的替代 |
| --- | --- | --- | --- |
| 语言 | Python 3（标准库为主） | 单机个人工具；文本解析/JSON/SQLite 都在标准库；零部署成本 | Node.js / Go |
| 存储 | SQLite（单文件） | 单用户单机、事务与索引够用、可直接拷贝备份、无需服务端 | PostgreSQL / MySQL（需常驻服务，超出个人工具规模） |
| 数据访问 | 手写模型驱动 DAO（`app/store.py`） | 需要审计留痕、不可修改字段、乐观锁等横切语义，ORM 反而要绕 | SQLAlchemy / Django ORM |
| 数据模型 | JSON 单一事实来源 + 代码生成 | 模型、DDL、文档、Excel 必须永远一致，人手同步必然漂移 | 直接手写 DDL / 用 ORM 模型类当源 |
| 前端 | 无（命令行 CLI） | 需求第 7 章先做数据与 AI 能力；界面属于后续步骤 | Web 界面（提前做会锁死未定型的数据契约） |
| 模型接入 | 标准库 `urllib` + 可注入 transport | 少依赖；transport 注入使全部 AI 逻辑可离线测试 | openai SDK / requests（为一次 HTTP POST 引入依赖不划算） |
| 飞书接入 | 标准库 `urllib` 直连开放平台 HTTP API | 只用到五六个接口；官方 SDK 会带入整套运行时 | lark-oapi |
| 迁移 | 生成式 DDL + `migrate_db.py` 补列补索引 | 单机单文件库，补列即可；迁移框架的复杂度用不上 | Alembic |
| 文档 | 生成式（模型文档）+ 手写（架构/接口/规范/ADR） | 字段级信息必须生成，否则一定与模型不一致 | 全手写（会漂移）/ 全生成（缺少为什么） |

## ADR-0001 技术栈限定为 Python 标准库 + SQLite

**状态**：已采纳

**背景**：这是给单个用户使用的个人成长档案系统，部署在用户自己的 Windows 机器上。数据量级为
「数千条工作事项 + 数万条原文片段」，并发只有一个人。

**决策**：产品代码只依赖 Python 标准库与 SQLite；不引入 Web 框架、ORM、迁移框架、HTTP 客户端库、
日志框架。唯一例外是需求文档提取脚本使用 `python-docx`（只读需求文档，不进产品代码路径）。

**理由**：①单机单用户不需要服务端能力，引入框架只增加长期维护面；②SQLite 单文件可直接拷贝备份、
可离线、无安装；③标准库已覆盖 JSON / SQLite / HTTP / 正则 / 哈希 / 压缩 / 时间，够了；④零依赖意味着
换个 Python 解释器就能跑，不会因为依赖升级而腐坏。

**后果**：需要自己写的东西：DAO、校验、迁移、CLI 框架（argparse 已够用）。这些都是本项目独有的语义
（审计、不可修改字段、来源追溯），自己写反而更直接。代价是没有 ORM 的便利，字段变更必须走模型流程。

**曾考虑**：FastAPI + SQLAlchemy + Alembic + React。放弃原因是它们服务于「多用户在线服务」这一不同问题，
会让本项目的核心（数据模型一致性与来源追溯）淹没在脚手架里。

## ADR-0002 数据模型单一事实来源 + 代码生成

**状态**：已采纳

**背景**：需求第 7 章要求交付「完整的数据模型和字段说明」。字段一旦分头维护（DDL 一份、文档一份、
代码里再一份），必然出现「文档说有这个字段，库里没有」这类漂移。本项目已经出现过一次：模板里写了
`trait_type` 覆盖四项分面，而枚举里没有。

**决策**：以 `schema/model.core.json`（骨架：约定、通用字段组、枚举、实体登记、需求覆盖矩阵）与
`schema/parts/*.entities.json`（分层业务字段）为**唯一人工维护源**；`tools/build_model.py` 合并校验后生成：

- `schema/model.json`：运行时元数据（含 `full_fields`），`app/model_meta.py` 只读它；
- `schema/schema.sql`：SQLite DDL（含 CHECK、部分唯一索引、外键、索引、拓扑排序后的建表顺序）；
- `docs/个人成长档案系统-数据模型设计 V1.0.md`：字段级设计文档；
- `docs/个人成长档案系统-数据模型字段清单 V1.0.xlsx`：给非开发者看的字段清单。

生成过程自带校验：引用完整性、枚举使用、必填与默认值冲突、组合唯一约束列、`min > max`、模板里
`实体.字段` 引用是否存在、DDL 能否在内存 SQLite 里真的执行起来。任一失败即非零退出。

**理由**：把「一致性」变成构建期错误，而不是运行期惊喜。

**后果**：不能手改生成物（会被下次构建覆盖，且 `check_all.py` 会报「生成物与模型不一致」）；
新增字段要走 core/parts，然后 `build_model.py` → `migrate_db.py` → 回归测试。

## ADR-0003 主键使用 UUIDv7（TEXT）

**状态**：已采纳

**决策**：所有实体主键为应用层生成的 UUIDv7 字符串（`app/ids.py`），不用 SQLite 自增整数。

**理由**：①时间有序，索引局部性好于 UUIDv4；②主键在写库前就已确定，便于先写关联再回填、
也便于 AI 建议里引用「待创建」的实体；③导出/迁移/合并数据时不会撞号；④多态引用（`entity_type` + `entity_id`）
需要一个全局唯一、跨表无歧义的 id。

**后果**：主键是 TEXT，占空间略大；必须显式 `NOT NULL`（SQLite 的 `TEXT PRIMARY KEY` 允许 NULL）。
已由 DDL 生成器保证。

## ADR-0004 模型驱动的数据访问层，写操作强制留痕

**状态**：已采纳

**决策**：`app/store.py` 的 `insert/update/soft_delete/log_action` 统一：按模型校验（未知字段直接拒绝、
必填/枚举/范围/类型校验）、自动填 `id/created_at/updated_at/revision`、每次写入追加一条 `audit_log`
（记录 before/after payload、actor_type、`proposal_id`、`job_id`）。

**理由**：需求 1.4③（重要数据保留来源和关联）、1.4⑦（允许用户随时修正）与 6.9（AI 变更审核）都要求
「谁在什么时候把什么改成了什么」可查。把留痕放在 DAO 层，业务代码就不可能忘。

**后果**：写入路径有统一的校验开销；`audit_log` 只增不改不删（用 `base_append_only` 字段组，没有
`updated_at/revision/deleted_at`）。绕开 DAO 直接用 SQL 写库属于违规（除导入片段时的 `write_audit=False`
批量插入这一处已知例外）。

## ADR-0005 软删除 + 乐观锁 + 不可修改字段

**状态**：已采纳

**决策**：①删除是软删除（写 `deleted_at`），查询默认过滤；唯一约束落成**部分唯一索引**，只约束未删除行；
②`update` 支持 `expected_revision`，不匹配抛 `Conflict`；③字段级 `imm` 标记表示「写入后不可修改」，
`update` 检测到对已有值的 `imm` 字段改动即拒绝。

**imm 的例外细则**：`imm` 字段允许「从空到有值」写一次（作业结束时补记 `duration_ms`/`token_usage` 就靠这个）。
原始正文（`source_document.raw_text`、`source_fragment.text`、`provenance_link.quote_text`）有值后再改必被拒。

**理由**：需求 1.4① 要求原始内容不得被 AI 覆盖；软删除保证「改错了还能追」；乐观锁防同一记录被两次
AI 审核互相覆盖。

**后果**：查询必须记得带软删除过滤（已在 DAO 里统一）；SQLite 的 NULL 语义使「含可空列的组合唯一约束」
失效，必须靠部分唯一索引 + 规则 J18 兜住。

## ADR-0006 来源追溯以 `provenance_link` 为中枢，多态引用 + 快照兜底

**状态**：已采纳

**决策**：任何档案记录都可以挂 `provenance_link`（`entity_type` + `entity_id` + `fragment_id` +
`relation_type` + `quote_text`），指向产生它的原文片段；跨实体的语义关系放 `entity_relation`。
多态引用列（`entity_type`/`from_type`/`to_type`/`owner_type`/`target_type`/`cited_entity_type` 等）
用构建期生成的 `entity_type` 枚举做 CHECK，并为每对 `xxx_type` + `xxx_id` 生成复合索引。
对「名称会变」的多态目标（如 `role_record.target_id`）额外存一份 `target_label` 名称快照。

**理由**：需求 1.4③「重要数据必须保留来源和关联关系」与 3 章「查看该主题下的原始资料」都依赖它。
快照兜底是因为多态外键没有数据库级完整性保证，目标改名或合并后仍需可读。

**后果**：多态引用列不能建真外键，完整性靠「代码 + CHECK + 规则」三层保证；合并记录时必须搬移多态引用
（`archive.merge_records` 的 `_move_rows`），这是已知的复杂度集中点。

## ADR-0007 AI 只提建议：一切 AI 产出落 `change_proposal`

**状态**：已采纳

**决策**：AI 提取的结果一律先写 `change_proposal` + `proposal_evidence`（含引用片段与原文摘句），
`status=pending`；只有用户在 `Review.confirm()` 里确认后，才由服务层按建议写入正式档案，并把
`proposal_id`/`job_id` 记进 `audit_log`。`material` 是唯一例外：AI 可直接写，但必须以 `status=draft` 落库。

**理由**：需求 1.4④（AI 只提建议，用户确认才改正式档案）与 6.9（确认/修改/拒绝/补充说明）。
把「建议」和「档案」分成两张表，是让「AI 有没有越权写档案」成为一个可 SQL 验证的问题。

**后果**：多了一层间接（确认前档案里看不到 AI 的成果），这是有意为之：演示库里 16 条 pending 是正常的
中间状态而不是缺陷。确认时缺必填字段会拒绝写入并提示用 `--set 字段=值` 补充，这保证了档案不会出现
「半条记录」。

## ADR-0008 提示词与工作流入库，文件是源、数据库是运行态

**状态**：已采纳

**决策**：`prompts/*.json` 是提示词与 Agent 工作流的**源文件**；`Extraction.seed_config()` 把它们
写进 `prompt_template` / `agent_workflow` 两张表（同名同版本则更新）。运行时从表里取「`is_active` 且
版本最大」的那条，并把 `prompt_template_id` / `workflow_id` 记进 `ai_job`。

**理由**：需求第 7 章交付物包含「Agent 工作流及提示词配置」，同时要求「结构化档案独立于 Agent」。
文件便于版本管理与评审，表便于运行时冻结「这次提取究竟用的是哪版提示词」。

**后果**：改提示词要跑 `ai seed`（或 `Extraction.seed_config()`）；`ai_job` 可回溯到确切版本；
不做热加载（个人工具，重跑一条命令即可）。

## ADR-0009 模型接入层：标准库 HTTP + 可注入 transport + 多级凭据回退

**状态**：已采纳

**决策**：`app/llm.py` 用 `urllib` 直连 OpenAI 兼容的 `/chat/completions`；`LLMClient(transport=...)`
允许注入假传输层；配置解析顺序为「显式参数 → `GROWTH_LLM_*` 环境变量 → `NEORIGIN_API_KEY` →
DSH profile 的 `apiKeyEnv` → `~/.dsh/.credentials.yaml`」。默认 `max_tokens=16384`。

**理由**：①AI 逻辑是本项目最难测的部分，transport 注入让 66 条相关用例全部离线跑（不联网、不花钱、不抖动）；
②凭据回退顺序让「直接用本机已在用的模型网关」成为零配置路径；③`max_tokens` 定得高是因为该网关的模型
是推理型：额度太小会全部消耗在 reasoning 上，`content` 返回空（实测踩过）。

**后果**：错误码直接映射到 `ai_job.error_code`（`parse_failed`/`model_error`/`timeout`/`rate_limited`/
`invalid_input`/`conflict`/`unknown`），失败作业不会留在 `running`。密钥只以掩码形式出现在输出里。

## ADR-0010 飞书接入支持双身份，凭据存放于统一的凭据文件

**状态**：已采纳

**决策**：`app/feishu.py` 支持应用身份（`tenant_access_token`）与用户身份（OAuth `user_access_token`，
`app/feishu_auth.py`，含本地回调服务器与自动续期）。凭据（`FEISHU_APP_ID`/`FEISHU_APP_SECRET`/
`FEISHU_USER_*`）写在 `~/.dsh/.credentials.yaml` 的 `refs:` 段，与模型密钥同一处；写入前自动备份。

**理由**：应用身份读不到用户「我的空间」的私有云文档（飞书的用户身份与应用身份是两套授权）；
用户明确要求凭据存起来而不是每次粘贴。凭据集中在 DSH 已有的凭据文件里，避免出现第二个藏密钥的地方。

**后果**：`feishu auth` 需要用户在开放平台配置重定向 URL（默认 `http://localhost:8765/callback`）；
凭据文件解析必须逐行严格（曾因 `\s*` 跨行导致空值被读成下一行的键名，已修）。凭据不进版本库、不落数据库。

## ADR-0011 导入管线：解析成片段并保留字符偏移，原文可逐字回溯

**状态**：已采纳

**决策**：导入把一份资料解析为「正文全文 + 有序片段」（`source_fragment`，含 `fragment_type`、
`heading_path`、`char_start/char_end`、`text_hash`、`parse_confidence`）。片段是 AI 提取与来源引用的
最小单位；`verify` 子命令逐片段校验 `raw_text[char_start:char_end] == text`。内容哈希（sha256）用于判重，
`.zip` 先解包再按目录导入（拒绝 zip slip 越界）。

**理由**：需求 1.4③ 要求来源可追溯，前提是「引用得回原文」。有了偏移，证据引用就不是「相似文本匹配」
而是可验证的切片。

**后果**：片段与正文必须同时写入且不可修改（`imm`）；解析器升级后旧片段的偏移不会被重写（旧资料需要
重新导入才会用新解析口径）。附件复制到「数据库同目录/attachments/」，因此备份必须连同附件目录一起。

## ADR-0012 数据库迁移策略：生成式 DDL + 补列补索引工具

**状态**：已采纳

**决策**：模型变更后，`tools/build_model.py` 重新生成 DDL；已有数据库用 `tools/migrate_db.py`
对照 `PRAGMA table_info` 补缺列（`ALTER TABLE ... ADD COLUMN`）与缺索引。不带数据搬迁的复杂变更
（改类型、拆表）由一次性脚本处理，脚本归档在 `tools/oneoff/` 并注明不可重跑。

**理由**：SQLite 的 `ALTER TABLE` 能力有限；个人单机库可以「补列 + 必要时重建库重新导入」，
不值得引入迁移框架。

**后果**：必填且无默认值的新列只能按可空加上并打印警告（需要人工决定回填值）；每次模型变更后
必须对 `data/*.db` 跑 `migrate_db.py --all` 并回归测试。

## ADR-0013 质量闸门与生成式文档

**状态**：已采纳

**决策**：`tools/check_all.py` 是唯一的「全绿」判据：模型构建校验 → 生成物与模型一致性 → DDL 在
SQLite 实跑 → `compileall` → 密钥扫描 → 全量单元测试。文档分两类：字段级文档由模型生成；
架构/接口/规范/ADR/部署由人（agent）以代码为准撰写并标注 `路径:行号`。

**理由**：需求（用户 m01579 指令）要求「不能仅以功能可以运行作为完成标准」。把检查固化成一条命令，
才能在每轮改动后真的执行它，而不是靠记忆。

**后果**：任何提交前都应跑通 `check_all.py`；生成物被手改会被闸门拦下。

## ADR-0014 事项级去重与主题归并推迟到第 5 步

**状态**：已采纳（阶段性）

**背景**：AI 提取出的新事项，与档案里已有的语义重复事项，理论上可以在确认时自动合并。

**决策**：第 4 步**不做**事项级模糊去重；只在「项目/系统/模块/领域已存在同名记录」时生成 `link` 建议
（复用已有记录、只补来源），并把语义重叠的提示留在模型输出与建议理由里。真正的归并属于第 5 步
（`theme_merge`：`work_theme` + `theme_member` 相似度）。

**理由**：模糊去重一旦自动执行就是「静默改档案」，违背 1.4④；而做成人肉审核又需要相似度与理由字段
（已在第 3 步的 `work_theme`/`theme_member` 里备好）。宁可先留下可见的重复，也不要悄悄合并错。

**后果**：档案里会暂时存在语义重复的事项（演示库即是），这是预期状态；`theme_merge` 落地前，
用户可用 `theme`/`merge` 命令手工归并。
