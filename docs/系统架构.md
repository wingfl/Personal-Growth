# 系统架构

本文回答三件事：系统由哪些部分组成、数据怎么流动、为什么这样做。具体函数签名与行号见 `docs/模块与接口.md`，「怎么改代码」的约定见 `AGENTS.md` 与 `docs/开发规范.md`。

## 1. 定位与边界

个人成长档案系统把散落的周报、月报、项目材料变成结构化经历，再从经历中提炼能力证据、成长轨迹，并与公开招聘市场对照。

明确的边界：

- **单机、单人、本地**。没有账号、没有服务端、没有云同步；数据库是一个 SQLite 文件。
- **只读界面**。Web 端只做展示与解释，所有写入留在 CLI（见 §7）。
- **事实优先**。AI 只产生「建议」，每条都带原文引用，人工确认后才进入正式档案；推断出来的证据标记 `is_fact=0`，与原文证据分开统计。
- **不抓简历、不碰个人信息**。市场数据只取公开招聘列表的公开字段。

## 2. 运行形态

| 形态 | 入口 | 依赖 | 说明 |
|---|---|---|---|
| 命令行 | `python -m app.cli ...` | 仅标准库 | 导入、提取、确认、目标、画像、市场入库 |
| 只读界面 | `python -m app.web` / `启动个人成长档案.cmd` | 前端需 Node 构建 | `127.0.0.1`，GET-only |
| 采集器 | `cd collector && node run.js` | Node、puppeteer-core | 独立进程，产出 JSONL 由 CLI 入库 |
| 启动器 | `tools/launch_ui.py` | 标准库 | 缺 dist 自动构建、找空闲端口、开浏览器 |

产品代码（`app/`）不引第三方库是硬约束：换机器、断网、没有 pip 都能跑。需要浏览器或 Node 的能力全部隔离在 `collector/` 与 `web/`。

## 3. 分层

```
资料层    source_document / source_fragment / attachment
   ↓ import（切片段、推断期间、归档附件）
经历层    work_item / project / business_system / function_module / work_domain / role_record
   ↓ 提取（AI 建议 → 人工确认）
AI 层     ai_prompt / ai_job / change_proposal / proposal_evidence
   ↓
成长层    capability / capability_evidence / growth_goal / growth_snapshot / growth_stage
   ↓
市场层    target_role / job_posting / job_requirement / salary_benchmark / market_snapshot
   ↓
展示层    app/web.py（只读 JSON API）→ web/（React）
```

50 个实体按 `layer` 分成 8 组（`00_base`、`01_source`、`02_experience`、`03_achievement`、`04_portrait`、`05_growth`、`06_ai`、`07_market`），分组的实际作用只有两个：生成 DDL 时的顺序、文档与模型文件的分段。

## 4. 数据模型

单一来源是 `schema/model.core.json`：实体、字段、枚举、规则、覆盖项都在这里，`tools/build_model.py` 生成 `schema/schema.sql` 与 `schema/parts/*.entities.json`，`app/model_meta.py` 在运行时加载它做校验。

几条贯穿全库的设计：

- **中文实体名、英文表名**。面向用户的实体叫「项目」「工作事项」，表分别是 `project`、`work_item`。这样做的好处是提示词、CLI 输出、界面文案可以直接用中文实体名，不用维护一套翻译。
- **统一字段**。所有实体都有 `id`（uuid7，时间有序）、`created_at`/`updated_at`、`revision`（乐观并发）、`origin`（user/import/ai/system）、`is_fact`、`review_status`、`deleted_at`（软删除）。
- **多态引用**。`provenance_link`、`entity_relation`、`change_proposal.target_id`、`capability_evidence.target_id` 都用 `(target_type, target_id)` 指向不同表；代价是没有数据库级外键，靠 `app/archive.py` 的引用扫描保证一致性。
- **审计**。`audit_log` 记录每次写库的操作人、动作、前后值；数据库触发器禁止对 `audit_log` 做 UPDATE/DELETE。
- **规则集中在模型里**。必填、枚举、范围、跨字段约束写在 `rules`，`_problems()` 按实体统一校验，CLI 与 Web 都复用同一套。

## 5. 存储设计

- 一个 SQLite 文件，WAL 模式，`foreign_keys=ON`，`busy_timeout` 5s。表 50 张、索引 228 个。
- 迁移由 `tools/migrate_db.py` 完成：拆分 DDL、比较现有表结构、缺表新建、结构变化（尤其是多态引用的实体类型枚举）则「建新表→复制→删旧→改名」重建，全程 `foreign_keys=OFF`，结束做 `integrity_check` 与 `foreign_key_check`。
- 三个库：`data/growth.db`（真实数据，已被 gitignore）、`data/demo.db`（可提交的演示库）、`data/demo.pristine.db`（演示基线）。闸门会检查后两者与模型是否同步。
- 备份：`app/backup.py` 用 SQLite 在线备份 API 生成时间戳文件，保留最近 N 份；迁移前也会自动备份到 `data/logs/`。
- 为什么不用 PostgreSQL：单用户、数据量在十万行以内、要求零运维和可拷贝。代价是并发写只有单写者，所以批量作业一律串行。

## 6. 后端模块

| 模块 | 职责 | 关键点 |
|---|---|---|
| `store.py` | 连接、CRUD、事务、审计、校验 | 写方法不自动提交；`history()` 按 `occurred_at, rowid` 倒序 |
| `archive.py` | 引用扫描、合并、软删除、回收站 | 合并会转移多态引用并写 `entity_relation(merged_into)` |
| `importers.py` | 文件/文本/目录导入、切片段、期间推断 | `infer_period(filename, default_year)` 支持无年份文件名 |
| `extract.py` | 资料→建议、审核、批量确认 | `Extraction.run`、`Review.confirm/confirm_batch` |
| `capability.py` | 能力词典、证据标注、画像聚合、岗位链路推断 | 逐字引用校验，不合格的跳过 |
| `roles.py` | 岗位链路模板（产品/设计/研发/测试/运营/通用） | 只产生 `is_fact=0` 的推断证据 |
| `projects.py` | 项目归并、介绍生成 | LLM 失败回落规则稿 |
| `market.py` | 薪资解析、岗位入库、分位统计 | 单样本时三分位相同，不制造分布 |
| `llm.py` | OpenAI 兼容网关客户端 | 超时、重试、`finish_reason` 透出 |
| `web.py` | 只读 JSON API + 静态文件 | 每线程一个 SQLite 连接 |

数据流（导入到画像）：

```
文件 → import_file → source_document + source_fragment
     → Extraction.run → change_proposal(+quote) → Review.confirm → work_item/project/...
     → capability map（原文证据） / capability infer（链路推断）
     → Review.confirm_batch → capability_evidence
     → /api/capabilities、/api/growth → 画像与轨迹
```

## 7. 后端设计评估

做得好的地方：

- **边界清楚**：`app/` 零依赖、Web 只读、采集器独立，任何一部分坏了不影响其他部分。
- **模型单一来源 + 生成式 DDL**：改字段只改 JSON，迁移脚本能自动补列/重建表，测试库与真实库用同一套迁移。
- **「建议—确认」两段式**：AI 永远不直接写正式档案，所有 AI 产出都能回溯到原文片段；这让「用 AI 处理真实经历」这件事在可信度上站得住。
- **批量作业可断点续跑**：每批提交、已有 pending 建议的事项跳过、失败保留现场。

明显的债务：

1. **`app/cli.py` 1713 行**，子命令与业务逻辑混在一起，提取类命令还在里面拼参数；应该拆成 `app/commands/` 一命令一模块。
2. **`app/web.py` 694 行**里 API、静态服务、聚合查询混写；规模再涨要拆 `app/api/`。
3. **多态引用没有数据库约束**，合并/删除的正确性完全依赖 `archive.py` 的扫描逻辑，缺少「引用完整性巡检」的命令。
4. **并发模型是单写者**，批量 AI 作业只能串行；多用户（一人一库）能绕开，但同一库内的并行仍受限。
5. **没有缓存层**，`/api/summary` 每次全表聚合；当前数据量（千级）没问题，万级要加物化快照（`market_snapshot`、`growth_snapshot` 已经是这个方向）。
6. **错误处理以异常字符串为主**，CLI 直接打印中文消息；缺少结构化错误码，未来接 Agent 时要补。

## 8. AI / Agent 接入

当前形态：

- **模型网关**：OpenAI 兼容接口，配置来自 `~/.dsh/.credentials.yaml`，默认 `deepseek-v4-1-flash`；`ai check` 可自检。
- **提示词在库里**：`ai_prompt` 存模板（带版本与 `job_type`），`ai_job` 记录每次作业的输入范围、状态、耗时、错误；`prompts/*.json` 是可提交的种子。
- **产出统一落到 `change_proposal`**：`change_type`（create/update/link）、`target_entity_type`、`payload`、`proposal_evidence`（逐字引用）、`status`。审核通过才写正式表，`final_payload` 留痕。
- **可靠性**：推理型模型输出预算默认 32768，`finish_reason=length` 时自动翻倍重试一次；503/超时按指数退避重试；每批提交。

Agent 接入（第 9 步，未实现）的预留设计：

- 对外只暴露三类别能力：**查询**（现有只读 API）、**建议**（生成 `change_proposal`）、**执行**（确认/拒绝建议）。Agent 不应直接写业务表。
- 用 `ai_job` 作为任务句柄：提交作业→轮询状态→取建议→人工或策略确认。天然支持长任务与审计。
- 需要补：稳定的 JSON schema 输出、错误码、幂等键（同一资料重复提取要能识别）、权限范围（哪些实体允许 Agent 建议）。

## 9. 前端设计

- React 18 + Vite + TypeScript；组件按 shadcn/ui 的方式落地（Radix + cva + Tailwind），没有引入组件库运行时。
- 设计 token 单一来源：`web/src/index.css` 的 CSS 变量（颜色、圆角、阴影）+ `tailwind.config.js` 的字号/间距映射；页面不写死颜色。
- 图表统一走 `components/charts/EChart.tsx`（ECharts 按需注册、跟随容器尺寸、亮暗主题、透明背景）。
- 数据获取只有 `useApi<T>()`：`loading / error / data / reload` 四态，页面必须处理空态与错误态。
- 路由六页：首页、成长档案、数据分析、能力画像、市场定位、目标与复盘、设置（设置入口在右上角）。
- 只读：没有 mutation，没有表单提交；需要写操作时给出 CLI 命令提示。

## 10. 安全与隐私

- Web 只绑定 `127.0.0.1`，静态文件做路径穿越检查，API 只读。
- 密钥只存在 `~/.dsh/.credentials.yaml`，不进仓库；`check_all.py` 第 6 步扫描所有跟踪文件里的凭据模式。
- 数据库、日志、附件、市场原始数据、前端构建产物、`node_modules` 全部 gitignore。
- 推送公开仓库前人工复核：真实库、导出文件、含本机路径的文档都不能进。
- 招聘数据只取公开列表字段；不使用登录态、不碰简历；采集器限速、失败即停。

## 11. 运维

- 启动：`启动个人成长档案.cmd`（GBK + CRLF）→ `tools/launch_ui.py` → 缺 dist 自动 `npm install && npm run build` → 开浏览器。
- 日志：`data/logs/`（提取、标注、项目介绍等后台作业），不进库。
- 质量闸门：`tools/check_all.py` 九步——模型构建、DDL、库同步、依赖边界、编译、密钥扫描、索引一致、单测、汇总。
- 代码索引：`tools/index_code.py build --changed` 生成符号/引用/调用索引，供检索与后续 Agent 使用；改了 `.py`/`.md` 后要重建，否则闸门第 8 步失败。

## 12. 演进方向

1. 拆 `app/cli.py` 与 `app/web.py`，把命令与 API 变成薄适配层。
2. 引用完整性巡检 + 更完整的合并/归档语义。
3. 成长快照与阶段对比（`growth_snapshot`/`growth_stage` 目前是 0 行），让「长期变化」有真实数据支撑。
4. 市场侧：JD 正文与要求解析（当前只有列表字段）、`salary_benchmark` 录入报告口径、周更快照与趋势。
5. Agent 接入：只读 API + 建议 API + 任务句柄，先服务「自动整理与补全」，再考虑写入授权。
6. 多档案库：一人一库的导出/导入（数据 + 配置），用于分享与迁移。
