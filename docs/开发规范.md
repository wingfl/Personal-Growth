# 开发规范（个人成长档案系统 V1.0）

## 0 这份规范怎么用

- 本文件只写**这套代码里真实存在的约定**，不抄通用教材。每条约定都给出来源：要么是可执行的门禁（`tools/check_all.py`）、要么是仓库里已有的决策记录（`docs/技术选型与决策记录.md`）、要么是现有代码的一致做法（`路径:行号`）。
- 效力分级：
  - **强制**：由 `python tools/check_all.py` 的 9 步质量闸门自动拦住（`tools/check_all.py:427`）。违反就跑不过。
  - **约定**：没有被自动检查，但现有代码一律这么做；改它要先改这份文件并说明理由。
  - **建议**：写在文末「待改进」，是观察到的隐患，不是现行规则。
- 历史决策不删不改：新增或推翻决策时，在 `docs/技术选型与决策记录.md` 末尾追加新 ADR（`docs/技术选型与决策记录.md:3-7`）。

**边界硬规则**

1. `app/` 不能引入第三方依赖（含 `requests`、`python-docx`、`pydantic` 之类）。需要新依赖时先走 ADR-0001 的「追加新 ADR」流程。当前 `.docx` 解析已用标准库 `zipfile` + `xml.etree.ElementTree` 实现（`app/importers.py:16`、`:238`），产品代码里没有任何 `python-docx` 引用。
2. 生成物与源文件**必须一起提交**：改了 `schema/` 源却忘了重跑 `build_model.py`，闸门第 1 步会警告「生成物在本次构建中变化（说明提交前未重新生成）」（`tools/check_all.py:97` `step_build`）。
3. 一次性脚本（`tools/oneoff/`）不得纳入 `check_all.py` 流程，也不得重复执行（`docs/部署与运维.md:193-194`）。
4. 新的开发工具放进 `tools/`；能被 `check_all.py` 复用的检查要接进闸门，不要只写成文档（现有先例：依赖边界、密钥扫描都是可执行检查，`tools/check_all.py:321`、`:357`）。

## 2 命名约定

### 2.1 模块与文件

- 模块名用**小写单词**，多词用下划线：`store.py`、`archive.py`、`importers.py`、`model_meta.py`、`feishu_import.py`、`feishu_auth.py`、`logging.py`、`backup.py`。不用缩写（`importers` 而非 `imp`）。
- 测试文件 `tests/test_<主题>.py`，功能步骤类用 `test_step<N>_<主题>.py`：`tests/test_step1_import.py`、`tests/test_step3_archive.py`、`tests/test_step4_extract.py`、`tests/test_zip_import.py`、`tests/test_feishu_sync.py`、`tests/test_feishu_auth.py`、`tests/test_backup.py`。

### 2.2 函数与变量

- 函数/方法/局部变量 `snake_case`。
- **模块私有**用单下划线前缀：`_Sink`（`app/importers.py:41`）、`_parse_markdown`（`app/importers.py:88`）、`_clean`（`app/archive.py:82`）、`_apply`（`app/extract.py:764`）。
- 「只给同层/上层用的内部方法」也用单下划线，例如 `Archive._insert`（`app/archive.py:85`）、`Store._write_audit`（`app/store.py:226`）。CLI 允许调用它们做展示（`app/cli.py:331` 用 `arc._label`），但库与库之间不要互相调私有方法。
- 公开常量 `UPPER_SNAKE`：`SUPPORTED_EXTS`（`app/importers.py:21`）、`DEFAULT_DB`（`app/store.py:16`）、`AUTO_FIELDS`（`app/model_meta.py:17`）、`DEFAULT_SCOPES`（`app/feishu_auth.py:35`）。
- 模块内私有常量 `_UPPER_SNAKE`：`_MAX_BYTES`（`app/logging.py:23`）、`_BACKUP_COUNT`（`app/logging.py:24`）、`_HEADING_RE`（`app/importers.py:169`）、`W_NS`（`app/importers.py:172`，命名空间常量按惯例全大写无前缀）。

### 2.3 异常类

自定义异常一律 `XxxError`，且**按层归属**、定义在抛出它的模块里：

| 异常 | 定义位置 | 语义 |
| --- | --- | --- |
| `ModelError` | `app/model_meta.py:22` | 元数据层：未知实体/字段/枚举、字段值非法 |
| `ValidationError(ModelError)` | `app/model_meta.py:26` | 校验问题集合，`problems` 里带多条中文说明 |
| `Conflict(ModelError)` | `app/store.py:19` | 并发冲突：`expected_revision` 不符或 `rowcount != 1` |
| `NotFound(ModelError)` | `app/store.py:23` | 记录不存在 |
| `ArchiveError` | `app/archive.py:36` | 档案层的业务拒绝（参数不完整、引用不存在、归并受阻） |
| `ExtractError` | `app/extract.py:67` | AI 提取与建议审核的业务错误 |
| `LLMError` | `app/llm.py:30` | 网关调用失败，带 `code`（`invalid_input`/`rate_limited`/`timeout`/`parse_failed`/`model_error`） |
| `FeishuError` | `app/feishu.py:23` | 飞书接口失败，带 `code`/`status`/`path` |
| `FeishuSyncError` | `app/feishu_import.py:27` | 同步编排层错误（无凭据、无候选） |
| `FeishuAuthError` | `app/feishu_auth.py:52` | OAuth 流程错误（无凭据、回调超时、令牌失效） |
| `BackupError` | `app/backup.py:33` | 备份/校验失败 |

- `ValidationError` 继承 `ModelError`、`Conflict`/`NotFound` 继承 `ModelError`：**捕获 `ModelError` 就等于捕获这一族**（`app/model_meta.py:26`、`app/store.py:19`、`:23`）。
- `LLMError.code` 会被写进 `ai_job.error_code`（`app/extract.py:263-264`），新增错误码时同步检查 `docs/部署与运维.md` 的故障排查表。

### 2.4 实体、字段与枚举命名

- 实体 id 用小写单数 snake_case 且**表名等于实体 id**（DDL 由 `tools/build_model.py:360` `gen_ddl` 生成）。
- 字段名小写 snake_case，布尔用 `is_`/`has_` 前缀（`is_fact`、`is_routine`、`is_representative`，如 `app/archive.py:85`、`app/cli.py:1048`），外键用 `<实体>_id`（`system_id`、`project_id`、`domain_id`，如 `app/archive.py:212`、`:238`）。
- 枚举 code 用英文小写 snake_case，展示文案走模型里的中文标签（`Model.enum_label`，`app/model_meta.py:69`）。资料类型就是这套写法的代表：`weekly_report`/`monthly_report`/`work_log`…（`app/importers.py:24-35`）。
- 枚举候选值在 CLI 里**从模型取**，不硬编码：`_enum_choices` 用 `Model.load().enum_values(...)`（`app/cli.py:214`）。
- 表/字段的增删改一律改 `schema/`，不要改生成物（见第 1 节）。

### 2.5 时间字段命名与格式

| 后缀 | 含义 | 例 |
| --- | --- | --- |
| `_at` | 精确时刻，UTC ISO8601 `%Y-%m-%dT%H:%M:%SZ` | `created_at`/`updated_at`（`app/store.py:129`）、`started_at`/`finished_at`（`app/extract.py:235`）、`occurred_at`（`app/archive.py:238`）、`deleted_at`、`reviewed_at` |
| `_start` / `_end` | 区间端点，可为日期或时刻 | `period_start`/`period_end`（`app/importers.py:348`）、`start_date`/`end_date`（`app/archive.py:303`）、`first_seen_at`/`last_seen_at`（`app/archive.py:281`） |
| `_date` | 纯日期 `YYYY-MM-DD` | `start_date`、`end_date`（`app/archive.py:303`） |

- 时间格式只有两个出口：`now_iso()`（时刻，UTC）与 `date_iso()`（日期），都用 `app/ids.py:18`、`:23`。
- 一个时刻字段要配一个精度字段：`occurred_at` 配 `date_precision`，精度取值 `day/week/month/quarter/year/unknown`，由 `precision_from_period()` 推导（`app/archive.py:40`）。**不要**新建「只精确到月」的时间类型，靠精度字段表达。
- 任何时间入库前都会被 `model_meta` 按字段类型校验格式（`app/model_meta.py:122`），别在业务代码里自己拼时间字符串。

### 2.6 CLI 命名

- 子命令用「名词组 + 动词子命令」：`ai extract`、`feishu pull`、`backup create`（`app/cli.py:1167`、`:1242`、`:1280`）。
- 参数用 kebab-case，目标属性自动是下划线：`--complexity-basis`（`app/cli.py:1110`）、`--no-attachments`（`app/cli.py:1282`）。
- 需要重复出现的参数用 `action="append"`，`dest` 用复数：`--from` → `dest="fragments"`（`app/cli.py:1158`）、`--alias` → `aliases`（`app/cli.py:1049`）。

## 3 数据模型变更流程

数据模型是单一事实来源，变更必须**按顺序**走完五步（顺序与命令来自 `docs/部署与运维.md:176-194`，闸门见 `tools/check_all.py`）：

```bash
# ① 改源：schema/model.core.json 或 schema/parts/*.entities.json
#    （字段/枚举/规则都改这里；不要碰 model.json 与 schema.sql）

# ② 重新生成：schema/model.json + schema/schema.sql + 两份模型文档
PYTHONIOENCODING=utf-8 python tools/build_model.py      # tools/build_model.py:524

# ③ 已有库补列（只增不减，先看再改）
python tools/migrate_db.py --all --dry-run              # tools/migrate_db.py:112
python tools/migrate_db.py --all

# ④ 全量闸门（模型构建 + 模型自洽 + DDL 实跑 + 库同步 + 依赖边界 + 编译 + 密钥 + 代码索引 + 用例）
python tools/check_all.py                               # tools/check_all.py:427

# ⑤ 回归：第 ④ 步已含全部用例（当前 133 条）；单跑用
PYTHONIOENCODING=utf-8 python -m unittest discover -s tests -v
```

**为什么不能手改 `schema/model.json` 与 `schema/schema.sql`**

- 它们是生成物，`tools/build_model.py` 下次运行会整体覆盖，手改的成果必然丢失（ADR-0002，`docs/技术选型与决策记录.md:49`、`README.md:19-20`）。
- 闸门第 1 步专门检查这一点：构建前后生成物哈希若变化，说明提交前没重新生成（`tools/check_all.py:97`）。
- 手改 `schema.sql` 还会让「模型 → DDL → 库结构」三者失去一致性，而第 2、3 步正是拿生成物互相验证（`tools/check_all.py:136`、`:237`）。

**其他硬规则**

- 给已存在的库补结构只能用 `tools/migrate_db.py`（只做 `ADD COLUMN` 与补普通索引，不删列、不改类型、不动数据；见 `tools/migrate_db.py:52`）。手工 `ALTER TABLE` 属于绕过工具，禁止。
- 必填但无默认值的新列：`migrate_db.py` 只能按可空列添加并给出警告（`tools/migrate_db.py:52`）。这是设计限制，遇到时应考虑给默认值，而不是手工改库。
- 改完模型要**同步更新被钉死的测试断言**（例如实体总数 `len(entities) == 45`，`tests/test_step1_import.py:59`）——它是有意的回归锚点。
- 模型里出现「必填 + 不可修改 + 有默认值」的组合会被闸门警告（当前有一条：`growth_snapshot.generation_trigger`，实测输出见 `tools/check_all.py:136` `step_model`）。新增字段请避免这种语义冲突。

## 4 代码规范

### 4.1 数据传递与序列化

- **不用 ORM**，不用 dataclass 做持久化模型。跨模块一律传 `dict`/`sqlite3.Row`，字段名就是模型字段名（ADT-0002 的落地方式，`docs/技术选型与决策记录.md:49`）。
- 写入前**必须**经过 `model_meta` 校验：`store.insert` 内部调 `validate_values(..., require_all=True)` 与 `defaults_for`（`app/store.py:129`）。业务层不要自己判断字段合法性。
- JSON 列显式序列化，且中文不转义：`json.dumps(..., ensure_ascii=False)`（`app/extract.py:222-237`；CLI 侧见 `app/cli.py:233` 的 `_alias_json`）。审计 payload 追加 `default=str` 兜底（`app/store.py:226`）。
- 读出 JSON 列时自己 `json.loads`，不要指望 DAO 反序列化（`app/store.py` 只做 SQL 映射）。

### 4.2 错误处理分层

- 每层只抛**本层的异常**，并保留中文原因（`app/archive.py:36`、`app/extract.py:67`）。
- 底层异常向上转换时**必须带上原因**：例如 `Extraction.run` 把任何失败包装成 `ExtractError("AI 作业失败（%s）：%s" % (code, exc))`（`app/extract.py:278`）；`Review.confirm` 把写入失败包装成「写入正式档案失败：%s」（`app/extract.py:694`）。
- 领域异常由 CLI 兜底转成退出码 2；未预期异常由 CLI 记日志并返回 3（`app/cli.py:1306-1317`）。业务模块**不要**自己 `sys.exit`，也不要 `print` 错误。
- 禁止静默失败。允许的例外只有三处，且必须留痕或降级可见：
  1. 证据片段关联失败时跳过该条并继续（`app/extract.py:820` `_link_evidences`）；
  2. 日志目录不可写时降级到 stderr 并打印警告（`app/logging.py:61-63`）；
  3. 极端情况下挂 `NullHandler` 保证命令不因日志崩掉（`app/logging.py:68-69`）。
- 失败作业要**留状态**：`Extraction.run` 出错时把 `ai_job.status` 置 `failed`、写 `error_code`/`error_message` 再抛（`app/extract.py:260-278`）。同类场景照此办理：不能让记录停在中间态。

### 4.3 中文文案

- 所有面向用户/日志的错误消息用中文，且给出**下一步动作**，例如：
  - 「未找到飞书应用凭据。请设置 FEISHU_APP_ID / FEISHU_APP_SECRET 环境变量，或写入 ~/.dsh/.credentials.yaml 的 refs 段，或放在 config/feishu.json。」（`app/feishu_import.py:75`）
  - 「暂无来源追溯记录…」（`app/cli.py:188` 起的 `trace`）
  - 「标记为推断（is_fact=false）时必须写明事实依据 fact_basis（数据规则 B6）」（`app/archive.py:85`）
- 引用数据规则时写明编号（如「数据规则 B6」），便于回溯 `schema/rules.json`。

### 4.4 事务与提交约定

- **`store` 不自动提交**（`app/store.py:254`）：谁的业务动作是一个完整事务，谁就负责 `commit()`。
- 现行分工：
  - `Archive._insert` / `link_fragment` / `merge_records` 在自己的事务边界提交（`app/archive.py:85`、`:146`、`:342`）；
  - `Extraction.run` 分两次提交：建作业一次、收尾一次（`app/extract.py:238`、`:282`）；
  - `Review.confirm/reject` 提交建议状态与正式记录（`app/extract.py:694`、`:747`）；
  - `FeishuSync.pull` 在内部提交（`app/feishu_import.py:182`）；
  - `create_backup` 在写完 `backup_record` 后提交（`app/backup.py:158`）；
  - CLI 层唯一显式提交在 `import` 命令收尾（`app/cli.py:45`）。
- 需要「全成功或全回滚」的多步操作，用 `with Store(...)`（异常自动 `rollback`，`app/store.py:57-60`）或显式 `try/except: store.rollback(); raise`（`app/archive.py:342` 的归并就是范例）。
- 批量导入时单文件失败**不**中断整批，但要在批次记录里体现（`app/importers.py:644-674`）。这是「部分成功可接受」的唯一场景。
- 不要在事务中间调用可能抛出的外部接口（模型、飞书）：`Extraction.run` 的做法是先把作业落库并提交，再调网关（`app/extract.py:222-242`）。

### 4.5 审计留痕

- 每次 `insert`/`update`/`soft_delete` 自动写 `audit_log`（`app/store.py:129`、`:162`、`:201`、`:226`）。业务代码不需要手动写审计。
- 非增删改的动作（确认/驳回/导出/归并等）用 `store.log_action(...)`（`app/store.py:219`）。
- 唯一允许关闭审计的地方是**导入片段批量落库**（`write_audit=False`，`app/importers.py:503`），这是 ADR-0004 明确记录的唯一例外（`docs/技术选型与决策记录.md:102`）。新增 `write_audit=False` 必须先改 ADR。
- 绕过 `Store` 直接执行写 SQL 属于违规（`docs/技术选型与决策记录.md:102`）；只读查询可以用 `store.query()`（`app/store.py:125`）。

### 4.6 日志

## 10 长任务与上下文纪律

这一节来自一次真实事故：2026-11-27 的一次长会话在请求阶段被网关拒绝，
错误是 `outbound body measures ~1,857,688 tokens ... status 413`，其中 `other` 维度约 167 万 token
（消息本身只有 17 万）。任务本身没有失败，但会话无法继续。下面的做法是为了让长任务
（批量提取、全量导入、整库迁移）在中断后能低成本接上，而不是靠一条超长会话硬撑。

### 10.1 长作业一律后台跑，输出落日志

```bash
# 反例：前台跑 40 分钟，终端和上下文都被占住
python tools/oneoff/_extract_all.py

# 正例：后台作业 + 日志文件，随时用 tail 看进度
python -u tools/oneoff/_extract_all.py --only-missing > data/logs/extract_all.log 2>&1
```

- `-u` 关掉输出缓冲，日志才能实时看到。
- `data/logs/` 已在 `.gitignore` 里，日志不会误入库。
- 看进度只取尾部：`tail -5 data/logs/extract_all.log`；排错用 `grep -n "✗\|Traceback" 日志`，
  不要把整份日志读进上下文。

### 10.2 批处理脚本必须可重入

- 提供 `--dry`（只预览）、`--limit N`（先跑一篇验证）、`--only-missing`（跳过已成功的）。
- 单条失败只记录、不中断整批；最后汇总「成功 / 跳过 / 失败原因」。
- 每篇处理完立即提交，进程被杀也只丢当前这一篇。

### 10.3 里程碑就提交

每完成一个可验证的小闭环（一段代码 + 用例 + 闸门）就提交一次，提交信息写清「改了什么、为什么」。
不要把几小时的改动攒在工作区——一旦会话/机器中断，未提交的东西就是纯风险。

### 10.4 上下文到六成就写交接

- 观察 `acp_status` 或界面上的上下文占用；超过约 60% 就先收束，不要等压缩提示。
- 交接摘要固定五段，存在仓库里（如 `docs/交接.md`）而不是只留在对话里：
  1. **目标**：这一阶段要做到什么，验收标准是什么。
  2. **已完成**：改动的文件与行为，附验证命令与结果（`check_all` 几步全过、多少条用例）。
  3. **未完成**：剩余事项，按优先级排列，每条写清下一步命令。
  4. **关键事实**：`路径:行号`、函数签名、枚举/默认值、踩过的坑（错误原文）。
  5. **环境**：数据库/日志位置、后台作业 id、需要的凭据来源（只写来源，不写值）。
- 新会话先读交接摘要，再动代码；不要凭记忆重做已经完成的部分。

### 10.5 关于压缩工具

本机 DSH 装了 `billion-context`（本会话的 `compress` 工具即来自它）。它按前缀缓存工作，
健康会话的缓存命中率在 96–99%；压缩动作会把已消费的对话换成摘要，**摘要里必须保住
用户目标、决策理由、`路径:行号`、错误原文和未完成事项**。
压缩阈值默认是窗口的 75%（`compress.maxContextLimit`），需要更早收束可以调低，
但改的是用户 profile，须先征得同意。
